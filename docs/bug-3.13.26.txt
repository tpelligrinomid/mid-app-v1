- Sync started at `14:45:39 UTC`, completed at `14:48:43 UTC`, processing 14 records
- Tasks were moved to "delivered" in ClickUp at approximately 9:45 AM EDT — the **exact same window**

**Root Cause Hypothesis:**
1. **Timestamp boundary exclusion:** The incremental sync likely uses `date_updated > last_cursor` (strict greater-than). If a task's `date_updated` in ClickUp exactly equals the cursor value, it gets permanently skipped.
2. **Cursor advancement before persistence:** The sync may be setting `last_modified_cursor` (currently `null` in `pulse_sync_state`) before confirming all fetched records are written to the DB.
3. **Missing `include_closed` parameter:** The ClickUp "Get Tasks" API excludes closed/delivered tasks by default. If the incremental fetch doesn't pass `include_closed=true`, any task moved to a "closed" type status (like "delivered") would be invisible to subsequent fetches.
4. **Orphaned sync runs:** The `13:15:35 UTC` sync that never completed may indicate the process crashed mid-sync, potentially advancing internal state without persisting data.

**Recommended Fixes:**
1. Change the incremental cursor comparison from `>` to `>=` (and deduplicate by task ID on upsert to handle re-processing)
2. Ensure `include_closed=true` is passed on all ClickUp task list API calls
3. Only advance the cursor **after** all records in the batch are successfully upserted to the DB
4. Add a **daily reconciliation pass** (full sync or targeted re-check) for all tasks with `status_raw = 'waiting on client'` that haven't been updated in 24+ hours — compare against ClickUp API and correct any drift
5. Investigate and clean up orphaned sync runs (those with `status: started` but no `completed_at`)
6. Populate and actively use `last_modified_cursor` in `pulse_sync_state` — it's currently `null`
