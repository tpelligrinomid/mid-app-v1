# Keep LibreChat, move every schedule out

Keep LibreChat as the chat front end and stop looking for a replacement. No product, open-source or hosted, beats it on all six requirements. The one gap that started this search, scheduled runs that carry the owner's MCP OAuth identity, goes unsolved across the whole category: n8n, Dify, Cassidy, Gumloop and Lindy either leave it out or don't document it. Only Archestra and Claude for Work document it properly, and each brings a dealbreaker of its own. Archestra's license changes once a company reaches 30 users, and MiD is about that size. Claude for Work runs Claude models only. The hybrid architecture already settles the question: if Trigger.dev owns every scheduled job, the front end only needs **an API that runs an agent as a named user**. LibreChat has one, its beta Agents API with per-user keys, but its docs don't say whether those calls use the user's stored MCP OAuth token. That is the single fact to test. **Open WebUI** is the fallback: it is the only front end whose docs explicitly say OAuth MCP works over its API once the user has signed in through the web UI. **Archestra** is the strongest product on paper but should stay a reserve option. **Claude Team/Enterprise** is the "buy" option, and it only makes sense if you drop the open-model requirement. The test plan at the end takes about a week and ends in a yes-or-no answer.

## Only five products clear the per-user MCP sign-in bar

Requirement 1, each employee signing in to our Supabase OAuth 2.1 MCP server with dynamic client registration (DCR), eliminates most of the field. Among self-hosted chat apps, only LibreChat and Open WebUI document shipped per-user OAuth with DCR. LibreChat prompts each user to authenticate and falls back to DCR when no client ID is configured ([LibreChat mcp_servers docs](https://www.librechat.ai/docs/configuration/librechat_yaml/object_structure/mcp_servers)). Open WebUI stores each user's grant "against their account alone. Nobody else inherits it" ([Open WebUI MCP docs](https://docs.openwebui.com/features/extensibility/mcp.txt)). AnythingLLM supports only static headers and has an open OAuth request ([#6396](https://github.com/Mintplex-Labs/anything-llm/issues/6396)). Chainlit's per-user OAuth sits in an unmerged PR ([#3013](https://github.com/Chainlit/chainlit/pull/3013)). LobeHub's DCR currently breaks against standards-conforming public PKCE clients, and the fix ([PR #17570](https://github.com/lobehub/lobehub/pull/17570)) is unmerged.

The agent builders do worse. Dify Community shares one workspace credential across all users. Its Enterprise edition forwards an SSO token in a header, which is not OAuth to the MCP server, and the docs exclude cron runs from that forwarding ([Dify Enterprise docs](https://enterprise-docs.dify.ai/en/3.13.x/administer/sso/mcp-identity-forwarding)). In Sim, MCP runs "with the permissions of the user who configured them" ([Sim docs](https://docs.sim.ai/agents/mcp)). n8n has true per-user credentials, but only on Enterprise, only as a Preview feature, and with no Schedule trigger among the supported triggers ([n8n end-user credentials](https://docs.n8n.io/administer/manage-credentials/end-user-credentials)). Hosted tools such as Cassidy and Gumloop do per-user OAuth ([Cassidy](https://docs.cassidyai.com/agents/connectors/mcp-servers); [Gumloop](https://docs.gumloop.com/help/skills-triggers-mcp/custom-proxied-hosted-mcp.md)). Neither documents which user's token an unattended run uses, neither offers skills in Git, and Lindy's own pricing puts each scheduled workflow at **1,000–2,500 credits** against a **5,000-credit** Team base ([Lindy pricing](https://www.lindy.ai/pricing)). That pricing model penalizes heavy automation, which is exactly the use you plan.

## Your architecture already makes the front end's scheduler irrelevant

Requirement 4 is where every platform falls short, and it is the requirement your hybrid design removes from the front end entirely. LibreChat's Scheduled Chats are "experimental" and off by default. Before a run, LibreChat checks every MCP tool, and any "authentication flow requiring interaction prevents the run" ([LibreChat scheduled chats](https://www.librechat.ai/llms.mdx/docs/features/scheduled_chats)). That is the failure tracked in [issue #16157](https://github.com/LibreChat-AI/LibreChat/issues/16157). [PR #16699](https://github.com/LibreChat-AI/LibreChat/pull/16699) adds only a host hook, so don't wait on it. Every serious competitor has the same weakness in some form. Gemini Enterprise schedules fail unless credentials are refreshed every 14 days ([Google Cloud docs](https://docs.cloud.google.com/gemini/enterprise/docs/agent-designer/schedule-agent)). Glean caps users at **10 active background agents** ([Glean docs](https://docs.glean.com/agents/concepts/schedule-triggers)). n8n's per-user credentials don't fire on schedules at all.

So the requirement becomes: **can Trigger.dev call the front end's agent API as Jane, so that Pulse MCP sees Jane?** LibreChat's beta Agents API exposes `POST /api/agents/v1/responses` and chat completions. It authenticates with per-user API keys or OIDC tokens belonging to an existing user, and management calls run "as the bound user with that user's permissions" ([LibreChat Agents API](https://www.librechat.ai/docs/features/agents_api)). The docs never say whether an inference call through that API reuses the user's stored MCP OAuth token and refreshes it. Open WebUI's docs do say so: API keys are per user, the API checks "the caller's access to each selected tool server," and OAuth MCP works once the key's owner has completed the flow in the web UI ([Open WebUI API endpoints](https://docs.openwebui.com/reference/api-endpoints)). That one documented sentence is Open WebUI's whole advantage.

There is also a front-end-proof route. You own Pulse MCP and its Supabase auth, so Trigger.dev could get a user-scoped token from your own backend and call the model and Pulse MCP directly, bypassing the chat app. This is an inference, not something any note verified. It costs some build work, but it makes R4 independent of whatever chat surface you pick, and you can keep it as an insurance policy if both front-end APIs disappoint.

## Archestra matches the spec, but the license changes at 30 users

Archestra is the only product whose primary docs cover the whole loop. Each person signs in once over OAuth 2.1, and tools set to "on behalf of the user" make "each person act as themselves" ([Archestra servers auth](https://github.com/archestra-ai/archestra/blob/main/docs/pages/mcp/authentication/servers.md)). Grants on each agent go to a user, team, role or everyone ([access control](https://github.com/archestra-ai/archestra/blob/main/docs/pages/admin/access-control.md)). Schedules carry an `actor_user_id`, documented as "the user the scheduled run executes as" ([MCP server reference](https://github.com/archestra-ai/archestra/blob/main/docs/pages/reference/archestra-mcp-server.md)). An A2A endpoint accepts a personal token that runs "as You" ([webhook/A2A](https://github.com/archestra-ai/archestra/blob/main/docs/pages/agents/triggers-and-channels/webhook-a2a.md)). It also pulls SKILL.md folders from GitHub on a 15-minute, hourly or daily sync ([skills importing](https://github.com/archestra-ai/archestra/blob/main/docs/pages/agents/skills/importing.md)).

Two problems keep it in reserve. First, the per-agent access control you need is Enterprise-licensed, and it is free only while the **whole company has fewer than 30 users**. Above that, pricing is quote-only ([pricing model](https://github.com/archestra-ai/archestra/blob/main/docs/pages/get-started/pricing-model.md)). At about 30 people, you would hit that limit with your first new hire. Second, the docs present Docker as a way to try it and Helm/Kubernetes as the production path ([deployment](https://github.com/archestra-ai/archestra/blob/main/docs/pages/admin/deployment.md)), which conflicts with the plan to host on Render. The project is also young (repo created July 2025, about 4,400 stars), and the notes found no independent hands-on reviews. Archestra becomes worth a look only if both LibreChat and Open WebUI fail the API-identity test, and only after a written license quote.

## Claude Team is the only credible "buy," and it means dropping open models

If you were willing to drop open models, Claude Team/Enterprise would be the least work. The Owner adds Pulse MCP once and each member connects their own account, through Anthropic's published client identity, DCR, or your own client ([Claude connector docs](https://claude.com/docs/connectors/custom/remote-mcp.md)). Routine actions "appear as you" ([Claude Code routines](https://code.claude.com/docs/en/web-scheduled-tasks)), and Cowork scheduled tasks now run remotely using the owner's connectors ([Claude Help](https://support.claude.com/en/articles/13854387-schedule-recurring-tasks-in-claude-cowork.md)). Skills are native SKILL.md with org provisioning ([Claude Help](https://support.claude.com/en/articles/13119606-provision-and-manage-skills-for-your-organization)). Thirty standard seats run roughly **$600–750/month** (secondary source: [tygartmedia](https://tygartmedia.com/claude-team-pricing-2026-standard-premium-seats/)).

It still doesn't fit as the whole OS. It offers **Claude models only**, so R3 fails outright. Routines are capped at a one-hour minimum interval and **100 scheduled runs per hour per account**, and they draw down subscription usage. Routines belong to individual accounts and can't be shared. A leaders-only Finance agent would depend on project sharing and group-scoped skills, and the notes could not confirm group-scoped project visibility. Scheduled jobs would also run in Anthropic's runtime instead of your Trigger.dev pipeline, which breaks the "own the runtime" principle. Claude Team works well as a personal assistant on top of Pulse MCP, and Pulse MCP is already connected to claude.ai today. It shouldn't become the platform.

## Test plan: one week, decided by one test

Before you start, add logging to Pulse MCP that records the authenticated user (`sub` and email) and role on every tool call. Create three test accounts: a leader, a regular employee, and one who never connects Pulse. Every test below is judged by what Pulse logs, not by what the chat shows. Time-box each platform to two working days.

**Test 1 is the deciding test: LibreChat Agents API as the user.** Turn on `remoteAgents`. Have the regular user connect Pulse MCP in the LibreChat UI, then create that user's API key. From a Trigger.dev task, call `/api/agents/v1/responses` with a prompt that forces a Pulse tool call. It passes if Pulse logs the regular user, not a shared or admin identity. Then wait past the Supabase access-token lifetime and run it again with nobody logged in. It passes only if LibreChat refreshes the token silently. **Test 2, failure behavior:** repeat with the user who never connected. It passes on a clean authorization error with no fallback to anyone else's token. **Test 3, access control:** share a Finance agent only with the leaders group. The regular user's key must be refused when it calls that agent through the API, not just hidden in the UI, and Pulse must enforce role scoping even if the agent leaks. **Test 4, skills from Git:** write a small sync script that pushes a repo of SKILL.md folders through the Management API, assign one skill to one agent's allowlist, and confirm an edit in Git shows up after the next sync. **Test 5, discovery:** remove the preconfigured client settings and confirm that DCR and RFC 9728 discovery work against the Supabase server from scratch. The notes flag RFC 9728 discovery as unverified for both front ends.

**If Tests 1–3 pass, the decision is LibreChat, final.** Turn off Scheduled Chats for everyone, document Trigger.dev as the only scheduler, and move on. If Test 1 fails, run the identical Tests 1–5 on Open WebUI (set `WEBUI_SECRET_KEY` first, and don't make OAuth MCP tools default-on). If Open WebUI passes, switch; it is a single container and simpler to run on Render than LibreChat's Mongo-plus-Postgres stack. Only if both fail do you choose between building the direct Trigger.dev-to-Pulse token path or getting an Archestra license quote and running the same suite there.

## Conclusion

The repeated platform churn came from treating the front end as the place where scheduled agents live. Every product that tries to own both the chat and the per-user scheduled identity either breaks on OAuth refresh, puts identity behind enterprise pricing, or locks you to one model vendor. Once Trigger.dev owns all scheduled work, the front end is replaceable, and comparing chat products mostly stops mattering. The decision then rests on one fact: whether a per-user API call makes Pulse see the right person.

Pulse MCP's own authorization ends up doing more of the work than any front end. Every serious option, including Claude Team, assumes the MCP server enforces row-level and role scoping itself, because front-end access controls hide agents but don't secure data. Leaders-only Finance and HR should be enforced in Pulse first and in the chat app second. If you make that choice now, a later switch of front end costs a migration weekend instead of a re-architecture.
